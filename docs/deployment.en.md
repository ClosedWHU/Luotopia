# Homepage Deployment

[简体中文](./deployment.md)

Production runs on Cloudflare Pages at `www.whu.sb`. For local development see
[development.md](./development.md).

## Cloudflare Pages

1. Create a Pages project in the Cloudflare Dashboard and connect
   [ClosedWHU/Luotopia](https://github.com/ClosedWHU/Luotopia)
2. Build configuration:
   - **Framework preset**: Astro
   - **Build command**: `npm run build`
   - **Build output directory**: `dist`
3. Set the [environment variables](#environment-variables)
4. Bind the custom domain in the Pages settings after the first deploy

Do not add a `wrangler.jsonc` to this project. Once present it becomes the source
of truth for the whole project configuration, and the environment variables and
bindings configured in the dashboard get overridden by the file — the risk far
outweighs the benefit (see [404 handling](#404-handling)).

### Build pipeline

`npm run build` is preceded by `prebuild`:

| Step | Purpose | On failure |
|------|---------|-----------|
| `check:aasa` | Validates `public/.well-known/apple-app-site-association` | Build aborts |
| `hot-update:generate` | Generates and signs `public/hot-update/manifest.json` | Build aborts without a signing key |
| `scales:generate` | Generates `public/scales/manifest.json` (unsigned) | Build aborts on invalid scale data |

So `HOT_UPDATE_ED25519_PRIVATE_KEY` is a **required** secret rather than an
optional one — but only for production builds, see below.

### PR preview builds

Pages builds a preview deployment for every pull request. Preview environments get no
secrets by default, so `hot-update:generate` throws and the whole build goes red —
every PR carries a failing check, and a wall of red Xs teaches people to stop reading
them.

**Do not put `HOT_UPDATE_ED25519_PRIVATE_KEY` in the Preview environment.** This is
the one secret in the repository whose leak is remote code execution: the parser
scripts it signs run inside **every installed app**. A preview build executes the PR's
own code, so anyone who can open a pull request can add a line to the workflow or a
build script and read the key out. An App Store Connect key can be revoked and
reissued; this one means rotating the signing public key, shipping a release, and
waiting for every client to update.

The fix is to make the requirement conditional rather than to relax it: **nobody reads
a preview deployment's manifest**, so there is nothing to sign. Add one variable to the
Pages **Preview** environment (Preview only — not "All environments"):

```
HOT_UPDATE_ALLOW_UNSIGNED=1
```

With it set, a keyless build will:

- still run every validation — the test-vector completeness check, checksums, version
  arithmetic — so a PR that adds a parser script without a test vector fails exactly as
  it would in production
- **not** write `manifest.json`, leaving the committed signed manifest in place. Not
  writing it, rather than writing an unsigned one, is the point: an unsigned manifest
  would deploy something every app rejects, and would leave a ready-made unsigned file
  sitting in the build directory
- print explicit warnings

Production behaviour is unchanged: no key, no build.

There is a second guard, for the case where someone sets the variable on **All
environments** to save a click. Cloudflare injects `CF_PAGES` and `CF_PAGES_BRANCH`, so
the script refuses an unsigned build when it finds itself on the production branch
(override the name with `HOT_UPDATE_PRODUCTION_BRANCH`, default `main`). Without that,
one dashboard mistake would silently stop production manifests being signed — scripts
change, the manifest is never re-signed, hot updates stop reaching clients, and the
build stays green.

### What does not work on a preview

Preview environments have no runtime secrets, so:

| Route | Behaviour on a preview |
|-------|------------------------|
| `/status` | 503 `not_configured`; the page shows its error card |
| `/api/releases*`, `/api/appstore/latest` | Anonymous GitHub rate limits without `GITHUB_TOKEN`; the download page may fall back to its static labels |
| Static pages, styling, interaction | All fine |

`UPTIMEROBOT_API_KEY` is read-only and low-risk in Preview — add it there if you want
PR reviews to show a real status page. Do **not** add the App Store Connect group.

## Environment variables

Set these under Pages → Settings → Environment variables. For local development put
them in `.dev.vars` (see `.dev.vars.example`); `.env.example` is the full list.

| Variable | Required | Notes |
|----------|----------|-------|
| `HOT_UPDATE_ED25519_PRIVATE_KEY` | Yes | base64 PKCS#8 Ed25519 private key, generated by `npm run hot-update:init-key`. **Production only** |
| `HOT_UPDATE_ALLOW_UNSIGNED` | No | `1` permits a keyless build (validate only — no signature, no manifest write). **Preview only**, see [PR preview builds](#pr-preview-builds) |
| `HOT_UPDATE_PRODUCTION_BRANCH` | No | Production branch name, default `main`; used to refuse unsigned builds on it |
| `UPTIMEROBOT_API_KEY` | For `/status` | A Read-Only key is enough |
| `GITHUB_TOKEN` | No | Raises the GitHub API limit for `/api/releases*` |
| `REPO` | No | Defaults to `ClosedWHU/Luotopia` |
| `APPSTORE_CONNECT` | No | `1` enables App Store Connect (TestFlight build numbers) |
| `APPSTORE_CONNECT_KEY_ID` / `_ISSUER_ID` / `_PRIVATE_KEY` | When enabled | PEM with literal `\n` newlines |
| `APPSTORE_BUNDLE_ID` / `APPSTORE_COUNTRY` | No | Default `sb.whu.luotopia` / `cn` |
| `UPTIMEROBOT_API_URL` | No | Defaults to `https://api.uptimerobot.com/v2/` |
| `STATUS_COUNT_DAYS` | No | Days of history, default 90, capped at 180 |
| `STATUS_SHOW_LINKS` | No | Whether probe URLs are published on the page, default `1` |
| `STATUS_TIME_ZONE` | No | Zone the day buckets are cut in, default `Asia/Shanghai` |
| `STATUS_CACHE_TTL` | No | Snapshot cache lifetime in seconds, default 300 |

With `APPSTORE_CONNECT` off, `/api/appstore/latest` falls back to the public iTunes
Lookup, which needs no JWT.

> [!CAUTION]
> Secrets belong in Pages, never in the repository. `.dev.vars` and `.env*` (except
> `.example`) are gitignored. The former `status` sub-project committed an `.env`
> holding a real API key — gitignore does **not** untrack files that are already
> committed, so `git rm --cached` has to come first.

## 404 handling

`src/pages/404.astro` builds to `dist/404.html`, and **that file is the
configuration**.

Pages decides between "custom 404" and "single-page application" purely on whether
the build output contains a top-level `404.html`: with one, a miss is answered by
that file at status 404; without one, Pages assumes an SPA and rewrites *every*
unmatched path to `/` at 200. This site had no `404.html`, which is why `/typo` —
and even `/missing.png` — used to come back as the homepage. That is not a dashboard
toggle being on; it is the default inference from a missing file.

Therefore:

- Pages has **no** `not_found_handling` setting. The
  `assets.not_found_handling: "404-page"` snippet in the docs belongs to **Workers
  static assets** (`assets.directory` + `main`), a different product.
- There is also **no** route table to maintain in the middleware. Misses are the
  platform's call, so new pages cannot be left unconfigured.

`functions/_middleware.ts` keeps only what the platform cannot do. For 404s that is
two things.

**Choosing the representation per client.** Browsers get the full 404 document;
`curl`, `wget` and HTTP libraries get one line of `text/plain`
(`404 Not Found: /path` plus the site root) instead of 34 KB of markup in a
terminal. The decision reads whether `Accept` explicitly names `text/html`, with
`Sec-Fetch-Dest` as the tie-breaker. A JSON 404 a Function produced itself (such as
`/api/*`) is left alone.

**Choosing the language.** There can only be one `dist/404.html`, so the nine
translations are ordinary routes (`/<locale>/404/`, built by
`src/pages/[lang]/404.astro`) and the middleware fetches the right one with
`ASSETS.fetch` and returns it **at status 404**. Locale precedence matches the rest
of the site: path prefix, then cookie, then `Accept-Language`. `ASSETS.fetch` goes
straight to the asset store and does not re-enter Functions, so this cannot recurse.
The `max-age=0, must-revalidate` header stays — a 404 must never stick, because the
path may exist after the next deploy.

That same `prefersHtml()` test is also the first gate of
[language negotiation](#language-negotiation) — a static build has no SSR, so
`Accept-Language` is likewise only readable at the edge.

Verify after deploying:

```sh
curl -i https://www.whu.sb/definitely-not-a-page   # HTTP/2 404 + text/plain
curl -s https://www.whu.sb/404 | head -c 120       # the 404 document itself
```

## Domains and middleware

`functions/_middleware.ts` maintains an allowlist: `localhost`, `127.0.0.1`,
`www.whu.sb`, `whu.sb` and `*.whu.sb` pass through; `*.pages.dev`, `*.workers.dev`
and any Host not on the list are 302-redirected to `https://www.whu.sb` (path and
query preserved). A new domain has to be added here or it will be redirected away.

### Language negotiation

The site is purely static, with no SSR, so `Accept-Language` can only be read at the
edge — `Astro.preferredLocale` is permanently `undefined` in a static build. The
middleware handles it after host canonicalisation and before `next()`, behind four
gates, none of which is optional:

| Gate | Condition | What it keeps out |
|------|-----------|-------------------|
| Representation | `prefersHtml()` | `_astro` bundles, fonts, `/api/*`, and **prefetches** (`sec-fetch-dest: empty`) |
| Path shape | `!looksLikeAsset()` | `/api/releases/latest`, `/favicon.svg`, `/scales/manifest.json` opened in an address bar |
| Already prefixed | `!hasLocalePrefix()` | Requests already on `/en/…` |
| Already chosen | no `luotopia_lang` cookie | Every visit after the visitor picked a language by hand |

Only then is `Accept-Language` parsed (a hand-rolled q-value parser; Workers has no
built-in matcher worth depending on) and folded onto our locales one subtag at a
time: `zh-TW` → `zh-Hant`, `en-GB` → `en`. `q=0` is an explicit refusal and is
skipped rather than fallen through. The result has to differ from the default locale
**and** the locale has to actually have that page (`TRANSLATED_ROUTES`) before a 302
is emitted.

That last condition is not optional either. Without it, `/status` with
`Accept-Language: en` 302s to `/en/status`, which 404s, whose fallback 302s back to
`/status`, which detects English again — an infinite loop.

**Detection writes no cookie; only `?lang=` does.** The switcher's links carry
`?lang=<code>`; the middleware answers with `Set-Cookie: luotopia_lang` (one year,
`SameSite=Lax`, `Secure`) and a 302 to the same URL without the parameter, and from
then on detection no longer overrides the choice. Inferring the choice from "the path
had a locale prefix" instead would get the direction wrong: on `/en/`, clicking a page
English does not have (the nav points at the Chinese original) would write
`luotopia_lang=zh-Hans` and silently reverse what the visitor asked for.

`?lang=` lands on where *that page* lives in the chosen locale, not on the same path
minus the parameter: `/status?lang=en` records `en` and stays on `/status` (English
has no status page), while `/features?lang=en` lands on `/en/features`. Other query
parameters survive; an unpublished locale (`?lang=ja`) is ignored entirely.

302 throughout, never 301 — a permanent redirect gets cached against the URL and
would keep sending the visitor to English after they changed their browser language.

A 404 on a locale-prefixed path is probed once against the unprefixed equivalent: if
that exists, 302 to it (the right answer while a locale is only partly translated);
if not, serve that locale's 404 document directly rather than spending another hop.
This is nominally Astro's `i18n.fallback`, which is not used because it conflicts
with `src/pages/[lang]/*` — see
[development](./development.en.md#what-a-partly-translated-locale-does). All ten
locales currently translate every route, so the first branch never fires; it stays
because "this locale is only half done" is a state the site can be in again at any
time.

`/status` with `Accept-Language: en` 302s to `/en/status` **because that locale
really has the page**. `pathInLocale()` is both the guard and the target: when the
target equals the input, nothing is emitted. Without that guard the sequence is
`/en/status` → 404 → fallback → `/status` → detected again, forever.

`/open` on the deep-link host *does* take part in negotiation, but as a server-side
rewrite rather than a redirect — see below.

### Deep-link host (luotopia.whu.sb)

The app registers `https://luotopia.whu.sb/*` as Android App Links (autoVerify) and
iOS Universal Links (applinks), one-to-one with in-app routes (GoRouter matches by
path). When the app is installed and verified the OS opens it and the request never
reaches us; otherwise the middleware rewrites HTML navigations on that host to the
`/open` landing page (original URL preserved), whose script maps it back onto
`luotopia://app/<path>` and offers "open the app / download".

The landing page **is** localized, but as a rewrite rather than a redirect: the
address bar has to stay on the original deep-link URL, because that URL *is* what the
page's script turns into `luotopia://`. The middleware picks `?lang=`, then the
cookie, then `Accept-Language`, and `ASSETS.fetch`es the matching `/<locale>/open/`.

`?lang=` is the one the app is expected to use. The app knows its own locale, which
beats inferring one from the OS — and the two disagree often enough to matter, the
common case being an English system running an app the user deliberately set to
Chinese. No cookie is written on this host: it is a different origin from
`www.whu.sb`, so a cookie set here would never be sent there and would only look like
a preference that never applies. An unpublished or malformed `lang` falls back to the
default locale's page rather than failing, so a bad parameter cannot break a deep
link.

Maintenance notes:

- `sha256_cert_fingerprints` in `public/.well-known/assetlinks.json` must match the
  **actually distributed signing certificate** (currently the release certificate
  and the repository's shared debug certificate). Update it whenever the signing key
  changes or Android verification breaks. Read the fingerprints with
  `apksigner verify --print-certs app.apk`.
- `public/.well-known/apple-app-site-association` is for Team ID `ZW372988NV`,
  served as `application/json` via `public/_headers`; it must be reachable **with no
  redirect**.
- Bind `luotopia.whu.sb` as a custom domain on the Pages project (DNS CNAME to
  Pages). The domain must go live **before** an app release, or neither platform
  completes verification at install time.
- The whole host is claimed by the app, so scanner probes and stale QR codes land on
  `/open` as readily as real routes. `src/config/deeplinkRoutes.ts` lists the app's
  top-level route segments (matching the first segment of
  `app/lib/app/router/app_route_paths.dart`); when the first segment is not in it the
  landing page adds "the app may not have this page, it will still try", but **the
  launch proceeds regardless** — a stale allowlist must never block a jump that would
  have worked. Only the first segment is checked on purpose: the app has hundreds of
  nested routes that change per release, so deeper matching is left to the client's
  own error page.

Validate:

```sh
npm run check:aasa
curl -sI https://luotopia.whu.sb/.well-known/apple-app-site-association
```

## Status page (/status)

`/status` replaces the separately deployed `status.whu.sb` (a Nuxt + naive-ui fork
of `imsyy/site-status`) and shares this site's design, navigation and dark mode.

| Layer | File | Responsibility |
|-------|------|----------------|
| Core | `functions/lib/uptimerobot.ts` | Cuts day buckets in `Asia/Shanghai`, builds `custom_uptime_ranges`, aggregates monitors/logs into the snapshot the page consumes (groups, per-day state, incident counts and durations). Runtime-agnostic — importable from Node and Workers alike |
| Endpoint | `functions/api/status.ts` | `GET /api/status`, derived snapshot cached in `caches.default`; `?fresh=1` bypasses the read but keeps a 60s floor |
| Page | `src/pages/status.astro` | Polls every 5 minutes; stops the clock while the tab is hidden and resyncs from the wall clock on return; the 30/90-day switch slices the same snapshot client-side |
| Local | `statusDevApi` in `astro.config.mjs` | Serves the same endpoint under `astro dev`, sharing the core above |

The 60s floor on `?fresh=1` is not decoration: a throttle that lives only in the
browser is a suggestion, and one client looping `?fresh=1` would spend the account's
API quota and take the status page down — the exact thing the page exists to report
on.

`days` is **not** accepted as a query parameter; only `STATUS_COUNT_DAYS` sets it.
It is part of both the upstream request and the cache key, so exposing it would hand
out unbounded cache-miss amplification.

Monitor naming in UptimeRobot drives the grouping: a name shaped like
`WHU.sb Backend (Cloudflare)` splits into group `Backend` and entry `Cloudflare`;
names that do not follow it land in a catch-all group and keep their full name.

### status.whu.sb migration

Configure a 301 from that subdomain to `https://www.whu.sb/status/` in Cloudflare
(Bulk Redirects or a single Redirect Rule); the DNS record can stay where it is. The
former standalone project has been removed from the workspace.

## Other deployment targets

### Cloudflare Workers (SSR)

If SSR is needed:

```sh
npx astro add cloudflare
```

Then set `output: 'server'` and the `cloudflare()` adapter in `astro.config.mjs`,
run `npm run build`, and deploy `dist/` or `dist/_worker.js` to Workers. Note this
changes how 404s are handled (see above), and `functions/` has to be migrated too.

### Vercel

Import the repository; Astro is detected automatically and the default Framework
Preset is correct. `functions/` follows the Cloudflare Pages Functions convention
and does nothing on Vercel — the `/api/*` routes would have to be rewritten as
Vercel Serverless Functions under `api/`.

### Static hosting

```sh
npm run build
# deploy dist/ to Nginx, GitHub Pages, Netlify, etc.
```

Likewise `functions/` will not run, so everything depending on `/api/*` (the
download page's version badges and changelog, all of `/status`) falls back to static
placeholders or an error state.

## Post-deploy checks

```sh
curl -sI https://www.whu.sb/ | head -1                          # 200
curl -i  https://www.whu.sb/definitely-not-a-page | head -1     # 404
curl -s  https://www.whu.sb/api/releases/latest | head -c 200   # release JSON
curl -sI https://www.whu.sb/api/status | grep -i x-status-source
curl -sI https://luotopia.whu.sb/.well-known/assetlinks.json    # 200, no redirect
```

Language negotiation:

```sh
# First-visit detection: expect a 302 to /en/
curl -sI -H 'accept: text/html' -H 'accept-language: en' https://www.whu.sb/ | grep -i '^location'

# Every route has a translation now, so expect a 302 to /en/status (not Pages' 308)
curl -sI -H 'accept: text/html' -H 'accept-language: en' https://www.whu.sb/status | grep -i '^location'

# A 404 comes back in the visitor's language, still at status 404
curl -s  -H 'accept: text/html' -H 'accept-language: ja' https://www.whu.sb/nope-not-a-page | grep -o '<html lang="[^"]*"'
curl -sI -H 'accept: text/html' -H 'accept-language: ja' https://www.whu.sb/nope-not-a-page | head -1

# The deep-link landing page follows the language, as a rewrite not a redirect
curl -s -H 'accept: text/html' -H 'accept-language: en' https://luotopia.whu.sb/anything | grep -o '<html lang="[^"]*"'
curl -s -H 'accept: text/html' 'https://luotopia.whu.sb/anything?lang=fr' | grep -o '<html lang="[^"]*"'

# The app's contract: these three must stay untouched by negotiation
curl -sI https://www.whu.sb/legal/terms.md | head -1
curl -s  https://www.whu.sb/data/legal.json | head -c 80
curl -s  https://www.whu.sb/data/friend-links.json | head -c 80

# Explicit choice: expect a 302 to /en/ plus Set-Cookie: luotopia_lang=en
curl -sI 'https://www.whu.sb/?lang=en' | grep -i '^location\|^set-cookie'

# Once recorded, detection stands down: expect 200
curl -sI -H 'accept: text/html' -H 'accept-language: en' \
     -H 'cookie: luotopia_lang=zh-Hans' https://www.whu.sb/ | head -1

# Non-document requests are untouched, prefetches included: expect 200
curl -sI -H 'accept: */*' -H 'accept-language: en' https://www.whu.sb/ | head -1
```

`X-Status-Source` on `/api/status` reads `api` (upstream call), `cache` (snapshot
hit) or `throttled` (`?fresh=1` inside the floor). A 503 `not_configured` right
after a first deploy means `UPTIMEROBOT_API_KEY` is missing.
